# 12단계 — 통합 검증, 실행 개선, 문서

SPEC §24, §27, §28을 마무리해줘. 이 단계는 "실제로 실행해 보고, 문제를 고치고, 그 과정을 기록하는" 단계다.
과제 평가 기준(기획과 구현의 일치, 주요 기능 정상 작동, UI 완성도, 개선 과정)을 염두에 두고 진행한다.

1. **기획 ↔ 구현 대조표** (docs/REQUIREMENTS_TRACE.md)
   - docs/ 의 기획 문서(제안서, 사용자연구계획, 맥락질의, 작업분석, 인터랙션분석, UI디자인방법론)와 SPEC에서 사용자 요구사항·주요 기능을 뽑아 표로 정리: 요구사항 | 근거 문서·절 | 구현 화면(경로) | 주요 파일 | 상태(구현/부분 구현/미구현)
   - "부분 구현·미구현"은 이유를 쓴다. 구현하지 않은 것을 구현으로 쓰지 않는다.
   - docs/DESIGN_RATIONALE.md 추적표에도 최종 구현 화면·파일 경로를 채운다.

2. **검증 체크리스트** — SPEC §27의 20개 항목을 하나씩 확인. 자동 테스트로 가능한 것은 테스트를 작성·실행, 수동 확인이 필요한 것은 확인 절차를 적는다.

3. **빌드·테스트 실제 실행** — 백엔드 `.\gradlew.bat clean build`, 프론트 `npm run build` / `npm run lint` / `npm test`. 결과(통과·실패 개수, 실패 메시지 요지)를 docs/TEST_RESULTS.md에 그대로 기록한다. 실패하면 고쳐서 다시 실행하고, 실행 못 한 항목은 이유를 적는다. 성공으로 표시 금지.
   - 6~9단계는 Claude 앱 채팅에서 빌드 없이 작성되었다(PROGRESS.md 참고). 컴파일 오류·테스트 실패가 있을 가능성이 높으니 여기서 먼저 잡는다.

4. **실제 실행 점검과 개선** — dev 프로필로 백엔드·프론트를 띄우고 브라우저로 직접 확인한다.
   - 반응형(모바일 375px, 태블릿 768px, PC 1280px), 키보드 접근성(Tab 순서, 포커스 표시, 대화상자 Esc), 색 대비를 점검하고 문제를 수정
   - 주요 흐름을 처음부터 끝까지: 조회·검색·필터 → 상세 → 지도 / 회원가입·로그인 → 습득물 신고 → 분실 신고 → 마이페이지 수정·삭제 / 반환 신청 → 관리자 처리 / 유사 물품 추천
   - 발견한 문제는 docs/PROGRESS.md 12단계 항목에 **"발견한 문제 → 원인 → 수정 내용 → 수정 파일"** 표로 남긴다(개선 과정 증빙)
   - 주요 화면 스크린샷을 docs/screenshots/에 저장(모바일·PC 각각, 파일명은 `01-home-mobile.png`처럼 순번-화면-기기). 브라우저 자동화 도구가 없으면 찍을 화면 목록과 방법만 적고 찍었다고 쓰지 않는다.

5. **사용성 테스트 준비 점검** (docs/USABILITY_TEST_READY.md)
   - 과업 A, B를 실제 브라우저(모바일 375px)에서 진행자가 따라 할 수 있는 단계 스크립트로 작성하고 직접 실행해서 막히는 지점을 기록·수정
   - Kakao 키 없는 상태에서도 두 과업이 끝까지 완료되는지 확인
   - 시연 데이터 초기화 후 같은 초기 상태가 재현되는지 확인
   - 연구계획 §7 기록 양식에 맞춘 빈 기록지 템플릿(참여자 ID P01~P05, 시작·종료 시각, 성공 여부, 도움 여부, 오류) 제공. 실제 결과 칸은 비워둘 것
   - 목표 80%(5명 중 4명)는 설계 목표로만 표기하고 달성 여부를 쓰지 않는다

6. **문서**
   - README.md(한국어): 맨 앞에 프로젝트 소개(해결하려는 문제, 대상 사용자, 목적)와 주요 기능 요약(스크린샷 포함), 그 뒤에 스택, 폴더 구조, 환경변수, MySQL 설정, 실행 명령, Kakao 키 발급·허용 도메인 설정, 테스트 계정
   - docs/API.md, docs/ERD.md(Mermaid erDiagram)

7. 마지막으로 구현한 기능 / 변경 파일 / 실행 방법 / 실제 테스트 결과 / 미구현 기능 / 사용자가 직접 설정해야 할 항목(DB 비밀번호, JWT 키, Kakao 키 등)을 정리해서 알려줘.
