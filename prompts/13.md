# 13단계 — 배포·공유와 과제 제출 자료

과제 제출물 4가지를 준비해줘.
① 소스 코드(GitHub 저장소) ② 실행 가능한 결과물 또는 배포 링크 ③ 개발 과정에서 사용한 프롬프트 전체(순서대로) ④ 프로젝트 설명·주요 기능 요약.
다른 사람이 링크나 명령 하나로 결과물을 확인할 수 있게 만드는 것이 목표다.

시작 전에 docs/PROGRESS.md와 docs/TEST_RESULTS.md를 읽는다. 12단계의 빌드·테스트가 통과하지 않았으면 배포 작업을 하지 말고 그 사실을 기록한 뒤 `PHASE_RESULT: FAILED - 12단계 검증 미통과`로 끝낸다.

## 1. 하나의 주소로 실행되는 배포 형태
- 프론트 빌드 결과를 Spring Boot가 함께 제공하는 **단일 서비스**로 만든다(같은 주소라 CORS 설정이 필요 없고, Kakao 허용 도메인도 하나로 끝난다).
  - 루트에 multi-stage `Dockerfile`: Node로 frontend 빌드 → 결과를 backend의 static 리소스로 넣어 Gradle 빌드 → JRE 이미지로 실행
  - `/api/**`, `/uploads/**`, 정적 파일이 아닌 경로는 `index.html`로 보내는 SPA 라우팅 처리(새로 고침·직접 주소 입력 시 404 방지). 테스트 추가
  - `VITE_KAKAO_MAP_KEY`는 빌드 인자로 받는다. 키가 없어도 대체 UI로 동작해야 한다
- **배포 시연용 `demo` 프로필**
  - 기본 프로필처럼 `JWT_SECRET` 필수, H2 콘솔·개발 전용 기능 비활성
  - DB가 비어 있을 때만 시연 데이터 생성(기존 DemoDataSeeder 재사용, "시연용" 표시 유지)
  - 시연 계정 비밀번호는 환경변수 `DEMO_ACCOUNT_PASSWORD`로만 받고 기본값을 두지 않는다(없으면 시작 실패 + 한국어 안내)
  - 시연 데이터 초기화는 관리자만
- DB는 환경변수(`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`)로 연결하고, 관리형 MySQL이 SSL을 요구하면 연결 옵션을 환경변수로 덧붙일 수 있게 한다
- 업로드 사진 저장 위치(`file.upload-dir`)를 환경변수로 바꿀 수 있게 한다. 플랫폼 디스크가 재시작 때 지워지는지 확인해서 DEPLOY.md에 한계로 적는다
- **로컬 공유용 `docker-compose.yml`**: MySQL 8 + 앱. `docker compose up --build` 한 번으로 http://localhost:8080 에서 실행되게 한다. 비밀값은 `.env.example`(빈 값 + 설명)만 만들고 실제 `.env`는 만들지 않는다
- Docker가 설치되어 있으면 이미지 빌드와 compose 실행을 실제로 해보고, 아래 스모크 테스트를 localhost에 돌려 결과를 기록한다. 없으면 이유를 기록한다

## 2. 배포 플랫폼과 배포 안내 (docs/DEPLOY.md)
- 단일 Docker 웹 서비스 + MySQL 호환 관리형 DB를 무료 또는 학생이 감당할 수 있는 비용으로 쓸 수 있는 조합을 **현재 공식 문서를 확인해서** 하나 추천하고 근거를 적는다(무료 한도, 잠자기 여부, 디스크 유지 여부). 대안 1개도 적는다
- 플랫폼 설정 파일이 필요하면 만든다(예: 해당 플랫폼의 서비스 정의 파일). 비밀값은 넣지 않는다
- 계정 생성·로그인·결제 정보 입력·비밀값 입력은 **사용자가 직접** 한다. Claude Code는 하지 않는다. DEPLOY.md에 사용자가 따라 할 단계를 번호로 적는다
  - 필요한 환경변수 표(이름, 설명, 예시 형식, 필수 여부, 생성 방법 — JWT 키 생성 명령 포함)
  - Kakao 개발자 콘솔에 배포 주소를 허용 도메인으로 추가하는 방법
  - 첫 배포 후 확인 순서
- `scripts/smoke-test.ps1 -BaseUrl <주소>`: 메인 페이지, 새로 고침이 필요한 SPA 경로(`/items`, `/map`), `GET /api/v1/categories`, `GET /api/v1/found-items`, 시연 계정 로그인(비밀번호는 실행할 때 입력받기, 파일에 저장 금지), 비회원의 보호 API 401 확인. 결과를 표로 출력
- 사용자가 배포를 마치고 주소를 `docs/DEPLOY_URL.txt`에 적어 두었으면 스모크 테스트를 그 주소로 실행해 결과를 docs/DEPLOY.md에 기록한다. 주소가 없으면 "배포 확인 대기"로 적고 배포했다고 쓰지 않는다

## 3. GitHub 공유
- 커밋 전에 비밀값 점검: `.env`, 실제 키·비밀번호·토큰 패턴이 작업 트리와 **git 이력 전체**에 없는지 확인하고 결과를 기록. 발견하면 커밋하지 말고 어떤 파일인지와 조치 방법(키 재발급, 이력 정리)을 사용자에게 알린다
- `logs/`(자동 실행 기록)와 업로드 파일, 빌드 결과물이 커밋되지 않는지 .gitignore 확인
- `git remote -v`로 원격 저장소가 있으면 push한다. 없으면 저장소를 만들거나 인증하지 말고, 사용자가 할 단계(웹에서 저장소 만들기 또는 `gh repo create`, `git remote add origin`, `git push -u origin main`)를 DEPLOY.md에 적는다. 공개 저장소로 할지 비공개로 할지는 사용자가 정하게 한다

## 4. 프롬프트 기록 (docs/PROMPT_HISTORY.md)
과제는 "최초 프롬프트부터 기능 추가·오류 수정·디자인 개선까지 순서대로" 전체를 요구한다. 아래 자료에서 **실제로 입력한 프롬프트**를 모아 시간 순서로 정리한다.
- 자료: `PROMPTS.md`, `prompts/00.md`~`13.md`, `prompts/fix-versions.md`, `prompts/_auto-rules.md`(자동 실행 때 각 단계 앞에 붙은 규칙), `logs/phase-NN-result.md`·`logs/phase-NN.jsonl`(실제 실행 기록), `docs/prompt-log/*.md`(사용자가 Claude 앱 채팅 등에서 입력한 프롬프트), `git log`, `docs/PROGRESS.md`
- 대화형 Claude Code 세션 기록이 `%USERPROFILE%\.claude\projects\` 아래에 이 프로젝트 폴더 이름으로 있으면, 그 안의 **사용자 입력만** 뽑아서 포함한다. 다른 프로젝트 폴더는 읽지 않는다
- 항목 형식: 순번 | 날짜 | 도구(Claude Code 자동 실행 / Claude Code 대화형 / Claude 앱 채팅) | 분류(최초 기획·환경 / 기능 구현 / 기능 추가 / 오류 수정 / 디자인 개선 / 검증·문서 / 배포) | 프롬프트 전문 | 결과 요약 | 관련 커밋
- 프롬프트 문장은 고치지 않는다(오타 포함 그대로). 비밀값·개인 연락처처럼 보이는 부분만 `[비공개]`로 가린다
- 어떤 단계가 어느 도구로 진행됐는지 사실대로 쓴다. 예: 6~9단계는 Claude Code 사용량 소진 후 Claude 앱 채팅에서 작성되었고 빌드는 12단계에서 확인했다
- 맨 앞에 요약 표(분류별 개수, 단계별 도구)를 둔다

## 5. 제출용 요약 (docs/SUBMISSION.md)
한 문서로 과제 제출물을 모두 찾을 수 있게 한다.
- 프로젝트 이름·한 줄 소개, 목적과 해결하려는 문제, 대상 사용자
- 사용자 요구사항 → 구현 기능 대응표(docs/REQUIREMENTS_TRACE.md 요약)
- 주요 기능 요약(스크린샷 링크), 사용 흐름 2개(분실자, 습득자)
- 링크: GitHub 저장소, 배포 주소, 로컬 실행 방법(docker compose 한 줄 + 수동 실행). 아직 모르는 링크는 `(배포 후 입력)`처럼 비워 둔다
- 시연 계정 안내(이메일만 적고, 비밀번호는 제출 시 따로 전달하라고 적는다)
- 테스트 결과 요약(docs/TEST_RESULTS.md의 실제 결과 그대로), 프롬프트 기록 링크
- 한계와 미구현 기능
- 끝에 **과제 요구사항 체크표**: 제출물 ①~④와 평가 기준 5개 각각에 대해 해당 파일·링크와 상태(완료 / 사용자 작업 필요 / 미완료)

## 6. 마무리
- docs/PROGRESS.md에 13단계 항목을 추가하고 커밋한다(`13단계: 배포 준비와 제출 자료`)
- 마지막 응답에 정리: 만든 파일, 실제로 실행·확인한 것과 결과, **사용자가 직접 해야 할 일**(배포 플랫폼 가입·환경변수 입력, Kakao 허용 도메인, GitHub 원격 저장소, DEPLOY_URL.txt 작성 후 `-From 13 -To 13` 재실행) 순서대로
- 완료 기준: Docker 이미지 또는 단일 서비스 빌드가 실제로 성공하고(Docker가 없으면 Gradle로 프론트 포함 빌드 성공), SPA 라우팅 테스트가 통과하고, DEPLOY.md·PROMPT_HISTORY.md·SUBMISSION.md가 만들어졌으면 SUCCESS. 실제 배포 확인은 사용자 작업이 끝난 뒤의 재실행에서 기록한다
