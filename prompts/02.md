# 2단계 — DB 스키마와 Entity

SPEC §18(DB 설계), §19(상태 관리)를 구현해줘.

- Flyway V1__init.sql: 9개 테이블, BIGINT PK, 좌표 DECIMAL(10,7), FK, NOT NULL, 카테고리/상태/날짜/좌표 인덱스, deleted_at
- CLAUDE.md "SPEC §18 대비 추가 컬럼"을 반영해: storage_locations의 contact_phone/operating_hours/pickup_guide, found_items의 private_features/version, 검색 동의어 테이블(예: 에어팟→이어폰, 버즈→이어폰, 카드지갑→지갑, 충전기→보조배터리처럼 가벼운 초기 목록)
- 카테고리 6종 기본 데이터는 마이그레이션으로 넣어. 시연용 건물/보관장소/물품/테스트 계정은 dev 프로필 전용 시더로 분리해 (SPEC §25)
- 시드 물품에는 SPEC §25의 10종에 더해 CLAUDE.md "데이터 규칙"의 평가 과업용 세트(파란색 파우치 정답과 오답 후보, 학생회관 건물, 다른 정답 세트 1~2개)를 넣어
  - 상태 분포: STORED(보관 장소 확정), PENDING_HANDOVER(보관 장소 확인 중), TEMPORARY, RETURN_PENDING, RETURNED가 모두 있어야 한다
  - 최소 2건은 발견 건물과 보관 건물이 달라야 한다
- dev 전용 시연 데이터 초기화: `POST /api/v1/dev/reset-demo`(dev 프로필 + ADMIN에서만 활성화) 또는 `gradlew.bat resetDemo` 태스크. 테스트 참여자마다 같은 초기 상태로 되돌리는 용도
- Entity, enum, Repository 작성
- Repository 테스트(H2)로 soft delete 제외 조회가 동작하는지, dev 외 프로필에서 시더와 리셋이 비활성인지 검증
