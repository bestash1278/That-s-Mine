### 발견해서 고친 앞 단계 문제 (실행을 막던 것)
- `JacksonConfig`가 `new ObjectMapper()`를 빈으로 등록 → JavaTimeModule이 빠져 LocalDate가 들어간 모든 응답·요청이 실패. 빈 등록을 없애고 Boot 자동 설정 사용
- 연관관계 필드에 대한 파생 쿼리 이름 오류 → 앱 시작 실패 가능
  `findByItemIdOrderBySortOrder` → `findByItem_ItemIdOrderBySortOrderAsc` 등 (FoundItemImage, StorageLocation, LostReportImage, ReturnRequest 리포지토리)
- `User`에 없는 `name()` 빌더 호출(DataInitializer, FoundItemControllerTest) → 컴파일 오류
- `findRecentNotDeleted`가 List를 반환하는데 서비스는 Page로 받음 → 컴파일 오류
- 검색 동의어를 `"a|b"`로 이어 붙여 LIKE에 넣음 → 동의어가 있는 검색어(이어폰 등)는 결과 0건. kw1~kw3 OR 비교로 수정, 동의어 term 중복 시 오류 나던 조회도 수정
- 테스트에 `@ActiveProfiles("test")`가 없어 MySQL에 접속하려 함. `@TestPropertySource`로 YAML을 읽으려던 설정도 프로필로 교체
- 카테고리가 세 군데(V1 SQL, 시드, 프론트 상수)에서 서로 달랐음 → SPEC §7 기준으로 통일(`V2__align_categories_with_spec.sql`, ID 1~6 유지)
- dev 프로필이 `ddl-auto: create-drop` + Flyway를 같이 써서 스키마가 어긋남 → Hibernate는 스키마를 건드리지 않음(`none`), Flyway가 관리
- 업로드한 사진을 제공하는 경로가 없었음 → `WebMvcConfig`(/uploads/**), Security 허용, Vite 프록시 추가
- 프론트 `isFutureDate`가 `new Date('YYYY-MM-DD')`(UTC 해석)를 써서 한국 시간에서는 **오늘 날짜가 미래로 판정** → 과업 B 제출 불가. 문자열 비교로 수정
- `index.css`가 Vite 템플릿 그대로라 Tailwind가 적용되지 않음 → Tailwind 지시문과 기본 스타일로 교체
- 목록 정렬을 클라이언트가 페이지 안에서만 하던 것 → 서버 정렬(sort 파라미터)로 변경
- 홈 화면이 `/found-items/recent`의 페이지 객체를 배열로 취급해 `map` 오류로 화면이 깨지던 것 → `data.content` 사용
- 오류 응답에 서버 내부 메시지(e.getMessage())가 그대로 노출 → 한국어 일반 메시지로 바꾸고 로그에만 기록

### 6단계 구현
**백엔드**
- `GET /api/v1/categories`, `/campus-buildings`, `/storage-locations?buildingId=` (ReferenceDataController/Service)
- 습득물 신고 검증 강화: 항목별 오류를 `400 { code: VALIDATION_ERROR, fieldErrors: {필드: 메시지} }`로 반환
  - 필수: 물품명, 종류, 발견 날짜(미래 금지, 오늘이면 미래 시각 금지), 발견 위치(건물 또는 직접 입력), 보관 상태
  - `HANDED_OVER`이면 보관 장소 필수, 공식 보관 장소를 고르면 이름·좌표를 보관 장소에서 채움
  - `PENDING_HANDOVER`·`TEMPORARY`이면 보관 위치를 저장하지 않음(화면에는 "보관 장소 확인 중"/"습득자가 임시 보관 중")
  - 건물만 고르면 `found_location`을 건물 이름으로 채움. **좌표는 임의로 만들지 않음**(7단계 지도 연결 전까지 null)
- 사진: 최대 3장, 5MB, 매직 바이트로 JPG/PNG/WebP 판별, 저장 파일명은 UUID + 감지한 확장자, 저장 실패 시 이미 쓴 파일 정리
- 상태 라벨을 SPEC과 일치: 신고 접수/보관 중/반환 진행 중/반환 완료/숨김 처리, 관리 부서에 전달 예정/전달 완료/습득자가 임시 보관 중
- 숨김(HIDDEN) 물품은 공개 목록·지도·상세에서 제외, 없는 물품은 404
- 시드 데이터를 `DemoDataSeeder` 하나로 통합(DataInitializer와 시연 초기화가 같은 데이터 사용)
  - SPEC §25 물품 10종 + 과업 A 세트(파란색 파우치 정답·오답 후보, 회색 가방 정답 세트 2), 모든 상태 포함
  - 정답 물품은 발견(도서관)과 보관(행정관 학생지원팀)이 다름
  - 시연 계정: `admin@demo.local`, `user1@demo.local`, `user2@demo.local` / 비밀번호 `demo.account-password`(기본 `demo1234!`, dev 전용)
  - 연락처는 `000-0000-0000 (시연용)`처럼 가상 값
- 신고자: 인증 전이라 **가장 먼저 만들어진 사용자를 임시 신고자로 사용**(TODO 8단계)

## 7단계 — 지도 기반 조회 및 위치 등록

작성: 2026-11-21, Claude 앱(채팅)에서 작성. **6단계와 마찬가지로 빌드·Vitest·브라우저 확인을 하지 못했다.** 특히 Kakao SDK 연동 부분은 실제 키로 동작을 확인해야 한다.

### 구현
**백엔드**
- `GET /found-items/map`: 발견 좌표가 없으면(건물만 고른 신고) 발견 건물 좌표로 영역을 판단(`COALESCE`), 최신순 최대 300건
- 응답에 `markerLatitude`, `markerLongitude`, `markerApproximate` 추가(건물 좌표로 대신했으면 true → 화면에 "건물 위치 기준")
- 지도 영역 검증: 범위 밖 좌표, 최소값 > 최대값이면 400 (`fieldErrors.bounds`)
- 테스트 `FoundItemMapApiTest` 4개 추가

**프론트엔드 — 지도 공통 모듈 (`src/components/map/`)**
- `useKakaoLoader`: SDK를 한 번만 동적으로 로드(`autoload=false&libraries=clusterer`), 10초 제한. 상태 `no-key | loading | ready | error`로 알리고 예외를 던지지 않음 → **키가 없어도 앱 전체는 정상 동작**
- `CampusMap`: 확대·축소 컨트롤, 이동, 클러스터링(축소 수준 5 이상), 같은 지점 물품은 마커 하나에 개수 표시, 선택 마커 강조. 리스너는 지도 생성 시 한 번만 등록하고 unmount 때 리스너·마커·클러스터 정리. 크기 변경 시 `relayout`
- `ItemMarker`: 색 + 글자(발/보/분/완) 핀 → 색만으로 구분하지 않음
- `MapLegend`(표시할 위치 종류 선택), `MapItemPopup`(마커를 누르면 사진·물품명·발견일·장소·보관 상태·상세 보기, 여러 개면 목록), `MapSearchFilter`(검색어·종류·상태·날짜), `LocationSearch`(교내 건물 이름 검색), `CurrentLocationButton`(권한 거부·실패 시 안내만 하고 지도는 계속 사용)
- `MapLocationPicker`: 지도 클릭으로 핀, 드래그로 수정, 건물 검색·선택, 현재 위치, **"이 위치로 선택"을 눌러야 폼에 반영**. 지도를 못 쓰면 **"시연용 위치 선택"** 제목과 안내로 실제 지도와 구분하고 건물만 고르게 함(좌표를 만들지 않음)
- `ItemLocationMap`: 상세 화면에 발견(빨강)·보관(파랑) 위치를 함께 표시. 지도를 못 쓰면 표시하지 않음(글 정보로 충분)

**프론트엔드 — 화면**
- `/map` 지도 조회(`MapPage`)
  - PC: 왼쪽 검색 조건·범례·목록 / 오른쪽 지도. 목록의 "지도에서 보기" → 해당 위치로 이동·마커 강조, 마커 선택 → 목록 강조
  - 모바일: 위 검색(상세 조건 접힘) / 가운데 지도 / 아래 선택한 물품 카드 또는 접이식 목록
  - 지도를 움직이면 "이 지역에서 다시 검색" 버튼 표시(작은 흔들림은 무시)
  - 분실 신고 위치(주황)는 범례에 보이되 "분실 신고 기능이 열리면 표시됩니다"로 비활성
  - 키 없음·로드 실패: 안내 + 같은 조건의 **건물별 목록** + "목록으로 보기"
  - 상세에 갔다 돌아오면 마지막 지도 위치 유지(새로 고침 시 초기화)
- 목록 ↔ 지도 전환 버튼(`/items` ↔ `/map`), 검색 조건 유지
- 습득물 신고 폼: 발견 위치에 "지도에서 위치 선택 (선택)", 직접 입력한 보관 장소에 "지도에서 보관 위치 선택 (선택)". 고른 뒤 "지도 위치 지정됨 · ○○ 근처 / 위치 변경 / 지우기". 건물을 아직 안 골랐으면 지도에서 고른(또는 120m 이내 가장 가까운) 건물로 채움. 발견·보관 좌표는 따로 저장
- 미리보기에 "지도 위치" 항목 추가

### 함께 고친 앞 단계 문제
- **목록 → 상세 → "목록으로" 시 검색 조건이 사라지던 문제**: `useItemSearch`가 `window.history.replaceState`로 주소만 바꿔 React Router가 몰랐음 → URL을 상태로 쓰도록 변경(`navigate(..., { replace: true })`)
- 목록 카드를 감싼 `div onClick` + 카드 안 `Link`가 동시에 이동해 기록이 두 번 쌓이던 문제 → 카드의 `Link`에 state 전달
- 검색어를 한 글자 칠 때마다 API를 호출하던 것 → "검색"(Enter)을 눌렀을 때 적용
- 처리 상태 필터가 없던 것 → 목록·지도에 추가(SPEC §8)
- 조회 화면 검색 영역이 진한 파란 배경에 진한 글자(대비 부족) → 흰 카드로 변경
- 상세 화면에서 **임시 보관(TEMPORARY) 물품이 "보관 장소 확인 중"으로 보이던 문제**(조건 순서 오류), 직접 입력한 보관 장소가 안 보이던 문제
- 목록 카드: 보관 정보가 "보관 장소 확인 중..."과 라벨로 두 번 나오던 것 정리, 사진 없을 때 빈 자리 표시
- `frontend/.env`가 Git 제외 대상이 아니었음 → 루트 `.gitignore`에 추가(실제 키가 올라가지 않게). `.env.example`의 예시 키 문자열을 진짜 키로 인식하던 것도 수정

## 8단계 — 회원가입·로그인 (JWT)

작성: 2026-11-22, Claude 앱(채팅)에서 작성. **6·7단계와 마찬가지로 빌드·테스트를 실행하지 못했다.**

### 구현
**백엔드**
- `JwtTokenProvider`(jjwt 0.13, HS256): 비밀키가 없거나 32바이트 미만이면 서버가 한국어 오류로 시작을 멈춤. dev/test 프로필은 고정 개발용 키, 기본(운영) 프로필은 환경변수 `JWT_SECRET` 필수
- `JwtAuthenticationFilter`: `Authorization: Bearer` 검증. 빈으로 등록하지 않고 SecurityConfig에서 직접 생성(서블릿 필터로 중복 등록되면 인증이 사라지는 문제 예방)
- 401/403을 공통 JSON(`UNAUTHORIZED`, `FORBIDDEN`, 한국어 메시지)으로 응답
- 권한 규칙
  - 비회원: 습득물 목록·상세·지도·최근, 카테고리·건물·보관 장소, 회원가입·로그인·이메일 확인, 업로드 사진
  - 로그인: 그 밖의 모든 API(습득물 신고, 내 정보, 이후 분실 신고·반환 신청)
  - ADMIN: `/api/v1/admin/**`, `/api/v1/dev/**` (+ `@EnableMethodSecurity`로 `@PreAuthorize` 동작)
- API: `POST /auth/signup`(가입 후 바로 토큰), `POST /auth/login`, `POST /auth/logout`, `GET /auth/check-email`, `GET·PATCH /users/me`
  - 이메일은 앞뒤 공백 제거·소문자로 저장, 중복 검사(동시 가입도 처리)
  - 비밀번호 8~64자 + 영문·숫자, BCrypt 저장, 확인 불일치 검사
  - 가입으로는 항상 USER(요청에 role을 넣어도 무시)
  - 로그인 실패는 이메일 존재 여부를 알 수 없게 같은 메시지
  - 비밀번호 변경은 현재 비밀번호 확인 필요
  - 토큰의 사용자가 없어졌으면(시연 데이터 초기화 등) 401 → 다시 로그인
- 습득물 신고자 = 로그인 사용자(6단계의 임시 신고자 제거)
- `@Valid` 검증 실패를 `fieldErrors`로 응답, `AccessDeniedException` 등이 500이 되지 않게 처리
- `backend/.env.example` 정리(JWT_SECRET 만드는 방법 포함)

**프론트엔드**
- `AuthContext`: 시작 시 저장된 토큰으로 `/users/me` 확인(`loading → authenticated | guest`), 로그인·가입·로그아웃
- `api/client.js`: 모든 요청에 토큰 첨부. 로그인 API가 아닌 곳에서 401이면 토큰 삭제 후 "로그인 정보가 만료되었습니다" 안내
- `ProtectedRoute`: 비로그인 → `/login?redirect=원래주소`로 보내고 **로그인 후 원래 화면으로 복귀**. 관리자 화면은 일반 사용자에게 안내만 표시(실제 권한은 서버가 판단). 돌아갈 주소는 앱 내부 경로만 허용(`//`, `https://` 차단)
- 보호 대상: 습득물 신고(작성·확인·완료), 분실 신고, 마이페이지, 반환 신청, 관리자
- 로그인 화면: 항상 보이는 label, 비밀번호 보기 버튼, 실패 시 메시지와 비밀번호 비우기, 개발 환경에서만 시연 계정 안내
- 회원가입 화면: 이메일 칸을 벗어나면 중복 확인, 비밀번호 조건 실시간 표시(색 + 체크 아이콘 + 화면낭독기 문구), 오류 요약과 첫 오류로 포커스
- 헤더: SPEC §6 메뉴(홈·분실물 조회·습득물 신고·분실 신고·지도 조회), 로그인 상태에 따라 로그인/회원가입 ↔ 마이페이지/로그아웃, 관리자면 "관리자" 메뉴. 현재 메뉴는 밑줄 + `aria-current`
- 하단 메뉴: 비로그인이면 "내 정보" 대신 "로그인"
- 마이페이지(최소): 닉네임·이메일·가입일, 로그아웃 (목록·수정은 9단계)
- 직접 로그아웃하면 작성 중이던 습득물 신고 초안도 지움(공용 기기). 토큰이 만료된 경우에는 지우지 않아 다시 로그인하면 이어서 쓸 수 있음

## 9단계 — 분실 신고 + 마이페이지

작성: 2026-11-22, Claude 앱(채팅)에서 작성. **6~8단계와 마찬가지로 빌드·테스트를 실행하지 못했다.**

### 구현
**백엔드**
- 분실 신고 API (`/api/v1/lost-reports`)
  - `GET /`, `GET /{id}`, `GET /map`: 비회원도 조회 가능. 신고자 정보(이메일·닉네임)는 응답에 없음
  - `POST /`(multipart, 201), `PATCH /{id}`(multipart), `PATCH /{id}/status`, `DELETE /{id}`: 로그인 필요, 수정·삭제는 본인만(403)
  - 분실 날짜 또는 추정 기간(`lostDate` ~ `lostEndDate`), 대표 추정 위치 1곳(건물 선택 또는 장소 이름) + 추가 설명, 지도 좌표(선택), 사진 0~3장
  - 검증: 미래 날짜, 끝 날짜 < 시작 날짜, 위치 없음, 길이, 좌표 범위 → `fieldErrors`
  - 접수 번호 `LR-000123`(ID 기반, `ReceiptNumbers`)
  - 목록·지도의 날짜 조건은 "분실 추정 기간이 검색 기간과 겹치는가"로 판단
  - 지도는 '찾는 중'만, 지점 좌표가 없으면 대표 건물 좌표로 표시(`markerApproximate`)
- 마이페이지 API: `GET /users/me/found-items`, `GET /users/me/found-items/{id}`(수정 화면용, 비공개 특징 포함·본인만), `GET /users/me/lost-reports`, `GET /users/me/return-requests`(조회만)
- 내 습득물 수정·삭제: `PATCH /found-items/{id}`(multipart), `DELETE /found-items/{id}`
- 수정·삭제 제한(`EditPolicy`, 서버에서 검증 → 409 `CONFLICT` + 이유 문장)
  - 습득물: 반환 진행 중(RETURN_PENDING)·반환 완료(RETURNED)·숨김(HIDDEN), 처리 중인 반환 신청(PENDING/APPROVED)이 있으면 수정·삭제 불가
  - 분실 신고: '찾기 완료'·'신고 종료'면 내용 수정 불가(삭제와 상태 되돌리기는 가능)
- 삭제는 모두 Soft Delete(`deleted_at`). 조회·지도·내 목록에서 빠지고 행과 반환 이력은 남는다
- 사진 처리를 `ImageStorageService`로 분리(습득물·분실 신고 공통). 수정 시 `keepImageUrls`(남길 사진) + 새 파일, 3장 제한, 다른 신고의 사진 URL 거부. 트랜잭션이 롤백되면 새로 쓴 파일을 지움
- 동시 수정은 기존 `@Version`(습득물) 충돌을 409 "다른 곳에서 먼저 변경"으로 응답
- Flyway `V3`: `lost_reports.lost_building_id`(FK, 선택) + 날짜·좌표·건물 인덱스
- 시연 데이터(dev): 분실 신고 4건(시연사용자2: 찾는 중 2·종료 1, 시연사용자1: 찾는 중 1), '은색 열쇠 꾸러미'(반환 진행 중)에 시연사용자2의 승인된 반환 신청 1건. 모두 `[시연용]` 표시

**프론트엔드**
- 분실 신고 작성(`/report-lost`): 조회 결과 없음 화면에서 넘어온 `keyword`·`categoryId`·`startDate`·`endDate`를 초기값으로 채우고 안내 표시. 조회 화면이 시작·끝 날짜를 모두 넘기도록 고침(예전엔 시작 날짜만 `date`로)
  - 날짜를 모르면 "기간으로 입력", 대표 위치 하나 + 추가 설명, `MapLocationPicker` 재사용, 사진
  - 로그인하지 않았으면 로그인 후 검색 조건이 그대로 담긴 신고 화면으로 돌아옴(8단계 redirect에 쿼리 포함)
- 완료 화면(`/report-lost/complete/:id`): 접수 번호, "마이페이지에서 수정·철회할 수 있습니다", 바로 볼 수 있는 습득물 미리보기
- 분실 신고 상세(`/lost-reports/:id`, 공개): 본인이면 상태 변경(찾았어요·신고 종료·다시 찾는 중), 내용 수정, 삭제
- 마이페이지 탭(내 정보·습득물·분실 신고·반환 신청, `?tab=`로 유지, 방향키로 탭 이동)
  - 내 정보: 닉네임·비밀번호 변경(현재 비밀번호 확인), 로그아웃
  - 목록 카드: 상태 배지(글자 + 색), 수정·삭제 버튼. 막힌 경우 버튼을 숨기지 않고 비활성 + 이유 문장(`aria-describedby`)
  - 삭제 전 확인 대화상자(되돌릴 수 없음 안내, 분실 신고는 '찾았어요' 대안 안내)

- 지도: 주황색 분실 신고 마커(범례 체크로 켜기), 마커 카드와 목록에 분실 신고 표시. 분실 신고를 못 불러와도 습득물 지도는 그대로

### 내린 결정
- **분실 신고에 건물 FK 추가(V3)**: 명세의 LOST_REPORTS에는 없지만, 건물만 고른 신고도 지도·추천(11단계)에서 위치를 쓰려면 필요하다. 습득물(`found_building_id`)과 같은 방식. 기존 컬럼은 그대로 둠
- **분실 신고 삭제는 언제든 가능**: 분실 신고는 반환 이력과 직접 연결되지 않는다. 대신 '찾기 완료'·'신고 종료'에서는 내용 수정만 막는다(무엇을 찾았는지 기록이 바뀌지 않게)
- **습득물의 처리 상태는 신고자가 못 바꿈**: 신고 접수→보관 중 등은 관리자(10단계). 보관 상태·보관 장소는 신고자가 바꿀 수 있다(6단계 신고 화면의 "맡긴 뒤 마이페이지에서 보관 장소를 바꿀 수 있어요" 안내와 맞춤)
- **다른 사람 신고 수정은 403**(존재 자체는 공개 조회로 알 수 있으므로 404로 숨기지 않음)
- **수정 API도 multipart PATCH**: 사진을 함께 바꿀 수 있게 등록과 같은 형식. 화면은 전체 값을 보냄
- **완료 화면의 미리보기는 임시 규칙**: 점수 추천(11단계) 전이라 "같은 종류 + 분실 시작일 이후 발견"으로 최대 3건. 화면에 "내 물건이라는 뜻은 아님"을 함께 표시. 11단계에서 `/lost-reports/{id}/matches`로 바꾼다
- **마이페이지 "유사 습득물 N건"**: 서버 필드(`similarItemCount`)와 화면 자리만 만들고 지금은 null이라 표시하지 않음(11단계에서 채움). 푸시·이메일 알림은 범위 밖
- 반환 신청 내역은 조회만(신청·취소는 10단계)

## 10단계 — 반환 신청 + 관리자 페이지

작성: 2026-11-22. 이번 단계부터 **테스트는 로컬 MySQL(`thatsmine_dev`)에서 서버를 띄워 확인**한다. 브라우저 화면 확인은 하지 못했다.

### 구현
**백엔드**
- 반환 신청(SPEC §15): `POST /found-items/{id}/return-requests`(201), `PATCH /return-requests/{id}/cancel`, `GET /found-items/{id}/return-requests/me`(상세 화면용: 신청 가능 여부·막는 이유·내 최근 신청)
- 관리자(SPEC §16, §20), 모두 `ROLE_ADMIN`(SecurityConfig + `@PreAuthorize`):
  - `GET /admin/found-items`(숨김 포함·검색·상태 필터), `PATCH …/status`, `PATCH …/storage`(실제 보관 위치 지정), `PATCH …/found-location`(발견 위치 수정, SPEC 목록에 없는 경로를 §16 "발견 위치 수정"을 위해 추가)
  - `GET /admin/lost-reports`(모든 상태), `GET /admin/return-requests`, `PATCH /admin/return-requests/{id}/status`
  - `POST·PATCH /admin/campus-buildings`, `GET·POST·PATCH /admin/storage-locations`(사용 중지 포함 목록)
- 규칙은 `ReturnPolicy`(순수 정적 규칙)에 모아 서버가 검증하고, 허용되는 다음 처리(`allowedNext`, `allowedStatuses`)를 응답에 담아 화면은 그 버튼만 보여준다
- 관리자 응답 DTO는 일반 응답과 분리: 신청자 이메일·소유 확인 설명·습득자 비공개 특징은 `AdminReturnRequestDTO`에만 있다
- Flyway 변경 없음(V3까지 그대로)

**프론트엔드**
- `/return-request/:id`(`ReturnRequestPage`): 물품 요약(발견한 곳/지금 보관 중인 곳 분리), 소유 확인 특징(필수)·추가 설명(선택), "담당자에게만 보인다", "소유권 증명이 아니다" 안내, 제출 중 버튼 비활성, 서버 `fieldErrors` 표시, 접수 후 찾아가는 방법(문의처·운영 시간·준비물)과 마이페이지 링크
- 상세 화면: 로그인했으면 신청 가능 여부를 불러와 막힌 이유(본인 신고, 이미 신청, 반환 진행 중 등)를 버튼 대신 보여줌
- 마이페이지 반환 신청 탭: 신청 대기 건 "신청 취소"(확인 대화상자)
- `/admin`(`AdminPage`, 탭 4개, 주소 `?tab=`): 반환 신청(승인·반려·반환 완료, 신청자 설명과 습득자 비공개 특징 나란히), 습득물(검색·숨김/복귀·보관 위치 지정·발견 위치 수정), 분실 신고(조회), 장소 관리(건물·공식 보관 장소 등록·수정·사용 중지, `MapLocationPicker` 재사용 + 위도·경도 직접 입력)
- `Modal`에 `max-h-[90vh] overflow-y-auto` 추가(긴 폼이 작은 화면에서 잘리지 않게)

### 내린 결정
- **신청 가능한 물품**: '보관 중'이거나 '습득자 임시 보관(TEMPORARY)인 신고 접수' 건. 보관 장소 미확정(전달 예정)·반환 진행 중·반환 완료·숨김은 막고 이유를 보여준다
- **본인이 신고한 물품에는 신청 불가**, 같은 사람의 처리 중(대기·승인) 신청은 물품당 1건
- **대기 신청은 여러 사람이 가질 수 있고 승인은 한 건만**: 승인하면 물품이 '반환 진행 중'이 되어 다른 신청은 승인할 수 없다. 승인 철회(반려)하면 보관 중(임시 보관이면 신고 접수)으로 복귀. 반환 완료 시 남은 대기 신청은 자동 반려(사유 자동 기록)
- **중복 반환 방지**: 물품 행 `SELECT … FOR UPDATE`(비관적 락) → 신청 행 락 순서로 잠그고, 잠근 뒤의 최신 상태로 전이를 판단. `@Version`은 신고자 수정 등 다른 경로와의 충돌용 보조 장치
- **취소는 신청자만, 신청 대기일 때만**. 승인된 신청은 관리 부서(반려 처리)에 문의
- **반려는 사유 필수**(신청자에게 그대로 보임). 승인·완료 메모는 선택
- **숨김은 처리 중 신청이 없을 때만**. 반환 진행·완료 상태는 관리자가 직접 못 바꾸고 신청 처리로만 바뀐다
- **보관 위치 지정과 처리 상태 연동**: 전달 완료로 지정하면 '신고 접수'는 '보관 중'으로, 전달 예정으로 되돌리면 '보관 중'은 '신고 접수'로. 반환 완료 물품은 변경 불가
- 신청의 "추가 설명"은 컬럼을 늘리지 않고 소유 확인 설명 뒤에 `[추가 설명]`으로 이어 저장
- 관리자 분실 신고는 조회만. 상태 변경은 신고자 본인 권한이라 관리자 기능에 넣지 않았다(SPEC §16 "신고 상태 변경"은 습득물 처리 상태로 구현)
- 건물은 삭제 없이 등록·수정만(SPEC §20 API 목록과 동일). 보관 장소는 삭제 대신 사용 중지
- 시연 데이터(시드)는 바꾸지 않았다. 점검 스크립트가 시연 데이터를 바꾸므로 끝에 `/dev/reset-demo`로 초기화한다

## 11단계 — 유사 물품 추천

작성: 2026-11-22. 테스트는 MySQL(dev 프로필) 기준으로 실행했다. 브라우저 화면 확인은 하지 못했다.

### 구현
**백엔드**
- `MatchScorer`(순수 규칙, SPEC §17): 카테고리 일치 30 + 물품명·특징 30 + 위치 근접도 25(Haversine, 100m 이내 만점·1.5km 이상 0점) + 날짜 15(분실 기간 안이면 만점, 끝난 뒤 14일에 걸쳐 0점). 합계 40점 미만은 추천하지 않고, 70 이상 "가능성 높음", 55 이상 "가능성 있음", 그 아래 "참고"
- 대상 제외: 반환 완료·숨김·삭제 물품, 발견 날짜가 분실 시작일보다 빠른 물품(논리적으로 맞지 않음)
- 물품명·특징 비교는 낱말 단위. 끝의 '색'을 떼어 "파란색/파란"을 같게 보고, `SearchSynonymService`의 동의어 사전으로 "에어팟 ↔ 이어폰" 같은 표현 차이를 흡수(낱말마다 한 번만 확장)
- `GET /lost-reports/{id}/matches`: 로그인한 신고자 본인 또는 관리자만(다른 사용자 403), '찾는 중'인 신고만(그 밖은 빈 목록), 점수 높은 순 최대 10건. 응답 `{ item(공개 목록 카드와 같은 DTO), score, level, levelLabel, reasons[] }`
- 마이페이지 `similarItemCount`: 찾는 중인 본인 신고에만 채운다. 후보 물품을 한 번만 읽어 신고마다 따로 조회하지 않는다(최대 500건 후보)
- Flyway 변경 없음

**프론트엔드**
- `MatchList`(`components/lost-report/`): 추천 카드(기존 `ItemCard`: 발견/보관 위치 구분 유지) + 등급 배지(색 + 글자) + "왜 추천했는지" 이유. 로딩·오류(다시 시도)·결과 없음(분실물 조회로 이어짐) 상태. 점수 숫자는 정밀한 값처럼 보이지 않게 숨김
- 분실 신고 완료 화면의 임시 미리보기(같은 종류 + 시작일 이후)를 추천으로 교체
- 분실 신고 상세: 본인 + 찾는 중이면 "비슷한 습득물" 영역(`#matches`로 바로 이동)
- 마이페이지: "유사 습득물 N건 보기 (소유 확정 아님)" 링크 → 상세의 추천 영역

### 내린 결정
- **비공개 특징(`private_features`)은 점수에 쓰지 않는다.** 순위·점수로 습득자만 아는 특징이 추측되는 것을 막기 위해서다(CLAUDE.md 설계 원칙 4). 응답에도 포함하지 않는다
- **추천은 신고자 본인에게만** 보인다. 분실 신고 상세 자체는 공개지만, 추천 목록은 조회 도구로 쓰이지 않게 로그인·소유자 확인을 둔다
- 점수가 아니라 등급과 이유를 보여준다. 모든 추천 화면에 "내 물건이라는 뜻은 아니며 실제 수령 시 담당자가 소유 여부를 확인합니다"를 표시하고, 자동 소유 판정은 하지 않는다
- 위치 정보가 없으면 위치 점수만 0이 되고 추천은 계속한다. 건물만 고른 신고·습득물은 건물 좌표로 거리를 계산한다(좌표가 있으면 지점 좌표 우선)
- 임계값(40점)과 등급 경계는 상수로 `MatchScorer`에 모았다. 실제 데이터로 조정할 설계 값이며 정확도를 검증한 수치가 아니다

| 서버 중복 제출 방지(SPEC §23) | 같은 사용자가 같은 내용(습득물: 물품명·종류·발견 날짜·장소 / 분실: 물품명·종류·분실 날짜·위치)을 60초 안에 다시 보내면 409. 사용자별 잠금(`DuplicateSubmissionGuard`)으로 동시 요청도 1건만 접수 | `DuplicateSubmissionGuard`, `FoundItemService`, `LostReportService`, 두 Repository의 `existsRecentDuplicate`, 두 Controller |
| 로그아웃 토큰 무효화(SPEC §13) | 토큰에 고유 번호(jti)를 넣고, 로그아웃하면 DB `revoked_tokens`(Flyway V4)에 올려 만료 전에도 401. 같은 계정의 다른 로그인은 유지, 만료된 기록은 로그아웃 때 정리 | `JwtTokenProvider.parseToken`, `TokenRevocationService`, `RevokedToken`, `JwtAuthenticationFilter`, `AuthController.logout`, `V4__revoked_tokens.sql` |

### 한계
- 중복 제출 방지는 **서버 한 대(JVM) 기준**이다. 서버를 여러 대로 늘리면 DB 쪽 제약이 필요하다.
- 60초가 지나면 같은 내용도 다시 등록할 수 있다(의도: 정말 같은 물건을 다시 신고하는 경우를 막지 않기 위함).
- 로그인 시도 제한은 여전히 없다. 토큰은 `localStorage`에 있다.
- 모든 요청이 `revoked_tokens`를 한 번 조회한다(기본키 조회). 사용자가 많아지면 캐시를 검토한다.

### 내린 결정
- **추천 플랫폼**: Aiven 무료 MySQL은 2026-11-06부터 신규 생성 불가·12-21 종료라 제외. Render는 MySQL을 제공하지 않아 외부 DB 필요 → TiDB Cloud Starter. TiDB는 MySQL "호환"이라 **Flyway 호환을 확인하지 못했음을 DEPLOY.md에 명시**하고 Railway(진짜 MySQL)를 대안으로 제시
- `demo` 프로필에서도 시연 초기화를 허용하되 ADMIN만(13단계 프롬프트 기준). 화면 버튼은 만들지 않았다
- 스모크 테스트의 비밀번호는 입력받는 것이 기본이고, 자동 실행용으로만 터미널 환경변수 `SMOKE_PASSWORD`를 허용(파일 저장 없음)
- 프롬프트 기록은 자료에서 **문장을 고치지 않고 옮기는 스크립트**로 만들었고, DB 비밀번호 값만 `[비공개]`로 가렸다. 자동 실행(`run-all.ps1`) 세션 기록은 없어 모두 대화형으로 표시. 세션 기록으로 확인하지 못한 항목은 그렇게 적었다
- "평가 기준 5개"의 다섯 번째는 저장소에 없어(과제 안내문 원문 없음) 체크표에 "사용자 작업 필요"로 남겼다
