# 사용성 테스트 준비 점검 (USABILITY_TEST_READY)

작성: 2026-11-22 (12단계). `docs/223625_장재영_사용자연구계획 (2).md` §5(과업·판정 기준)·§7(기록 양식)에 맞춘 **진행 준비 문서**다.

> **이 문서는 사용성 테스트를 수행한 결과가 아니다.** 사람 참여자를 대상으로 한 테스트는 하지 않았고, 성공률·소요 시간은 측정하지 않았다. 아래 "직접 실행한 점검"은 헤드리스 Chrome(375px)을 자동으로 조작해 두 과업이 끝까지 완료되는지 확인한 것이며, 사람이 겪는 어려움이나 걸리는 시간을 보여 주지 않는다.
> 목표 "5명 중 4명 이상(80%) 성공"은 **설계 목표**일 뿐이며 달성 여부를 기록하지 않는다. 연구계획의 수치·발화는 모두 가상 사례다.

## 1. 진행 전 준비 (참여자마다 반복)

| 순서 | 할 일 | 방법 |
|---:|---|---|
| 1 | MySQL 실행 확인 | `mysql --version`, 서비스 실행 중인지 확인. DB `thatsmine_dev`가 없으면 `CREATE DATABASE thatsmine_dev CHARACTER SET utf8mb4;` |
| 2 | 백엔드 실행(dev 프로필) | `cd backend` → `$env:DB_PASSWORD="…"` → `.\gradlew.bat bootRun --args="--spring.profiles.active=dev"` |
| 3 | 프론트 실행 | `cd frontend` → `npm run dev` (Kakao 키를 쓰지 않으려면 `frontend/.env`의 `VITE_KAKAO_MAP_KEY`를 비워 둔다. 두 과업은 키 없이 끝까지 된다) |
| 4 | **시연 데이터 초기화** | 관리자 로그인 후 `POST /api/v1/dev/reset-demo`. 화면 버튼은 없으므로 `python backend/scripts/check_demo_reset.py`를 쓰거나(초기화 후 상태 요약 출력) 아래 명령을 쓴다. 초기화하면 시연 계정이 다시 만들어지므로 **열려 있던 로그인은 만료**된다 |
| 5 | 기기 확인 | 같은 기기·같은 브라우저 크기로 모두 진행한다. 모바일은 실제 스마트폰(`npm run dev -- --host` 후 `http://<PC의 IP>:5173`) 또는 개발자 도구의 375px 화면 |
| 6 | 사진 준비 | 참여자 기기의 앨범(또는 PC 폴더)에 `frontend/public/demo-photos/umbrella-black-1.jpg`, `umbrella-black-2.jpg`를 넣어 둔다 |
| 7 | 시작 화면 | 과업 A: 로그아웃 상태의 홈(`/`). 과업 B: 아래 §3의 "로그인 처리" 결정에 따른다 |

초기화 명령 예(PowerShell):

```powershell
$login = Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/v1/auth/login -ContentType 'application/json' -Body '{"email":"admin@demo.local","password":"demo1234!"}'
Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/v1/dev/reset-demo -Headers @{ Authorization = "Bearer $($login.data.accessToken)" }
```

시연 계정(dev 프로필, 비밀번호는 환경변수 `DEMO_ACCOUNT_PASSWORD`, 없으면 `demo1234!`): `admin@demo.local`(관리자), `user1@demo.local`, `user2@demo.local`.

## 2. 과업 A — 물건 찾기 (3분)

**진행자 안내 문구** (연구계획 §5 그대로):

> “오늘 도서관에서 파란색 파우치를 잃어버렸다고 생각해 주세요. 안내 자료에서 주어진 특징에 맞는 물건을 찾고, 현재 어디에 보관되어 있는지 알려 주세요.”

| 항목 | 내용 |
|---|---|
| 시작 | 안내가 끝난 직후부터 시간 측정. 시작 화면은 로그아웃 상태의 홈 |
| 정답(세트 1) | **파란색 파우치** — 발견: 도서관 3층 제2열람실 · 보관: **행정관 학생지원팀**(발견 장소와 보관 장소가 다른 건물) |
| 오답 후보 | 남색 파우치(도서관 로비, 보관 장소 미확정), 파란색 필통(도서관), 같은 이름의 **반환 완료** 파란색 파우치(학생회관, 다른 날짜) |
| 정답 교체용 세트 2 | **회색 가방** — 발견: 공학관 · 보관: 행정관 학생지원팀 / 오답 후보: 회색 에코백(인문관). 안내 문구는 "공학관에서 회색 가방을 잃어버렸다"로 바꾼다 |
| 성공 | 도움 없이 3분 안에 **물건과 보관 장소를 모두** 맞힘. 오답·시간 초과·진행자 도움은 실패로 기록한다 |
| 진행자가 말하지 않는 것 | 검색어, 메뉴 위치, "상세 화면을 눌러 보라" 같은 안내 |
| 완료 후 안내 | 물건을 찾았더라도 실제 수령 전에는 담당자가 소유 여부를 확인한다는 점(상세 화면에도 표시됨) |

기대 경로 예: 홈에서 검색어 입력 또는 "분실물 찾기" → 조회 목록(카드의 "발견"과 "보관" 줄) → 후보 상세 → "지금 보관 중인 곳" 확인. 지도는 쓰지 않아도 된다.

## 3. 과업 B — 습득물 신고 (5분)

**진행자 안내 문구** (연구계획 §5):

> “학생회관에서 검은색 우산을 주웠다고 생각해 주세요. 카드에 적힌 날짜, 장소, 종류, 특징을 보고 신고해 주세요.”

참여자에게 줄 **카드 예시**(날짜는 진행 당일로 바꾼다):

| 항목 | 카드에 적을 내용 |
|---|---|
| 발견 날짜 | (진행 당일) |
| 발견 장소 | 학생회관 |
| 종류 | 우산(앱의 분류에서는 "의류·잡화") — 카드에 **"우산 = 의류·잡화"를 함께 적거나** 진행자가 분류 이름은 안내하지 않기로 미리 정한다 |
| 물품명·특징 | 검은색 우산, 검은색 장우산·손잡이는 갈색 나무 |
| 사진 | 준비한 예시 사진 중 선택(선택 동작만 시험) |
| 보관 상태 | **"관리 부서에 전달 완료 — 학생회관"** (아래 막히는 지점 3번 참고) |

| 항목 | 내용 |
|---|---|
| 시작·종료 | 시작부터 제출 완료 화면 도달까지 측정. 5분이 지나면 중단하고 미완료로 기록 |
| 성공 | 도움 없이 필수 내용(날짜·장소·종류·물품명)을 카드와 같게 입력하고 **제출 완료 화면(접수 번호)** 에 도달 |
| 주의 | 제출하면 시연 DB에 **실제로 저장**된다(외부 시스템으로 전송되지는 않는다). 참여자마다 진행 후 시연 데이터를 초기화한다 |
| 로그인 처리(진행자가 정할 것) | 습득물 신고는 로그인이 필요하다. ① 진행자가 `user2@demo.local`로 미리 로그인해 둔 상태에서 시작하거나 ② 로그인 과정을 과업 시간에 포함한다. 연구계획에는 로그인이 명시돼 있지 않으므로 **어느 쪽이든 5명에게 똑같이 적용하고 기록지에 적는다** |

실행: `node scripts/browser/flows.mjs`(Kakao 키 없음, MySQL dev 서버). 결과 36단계 모두 통과(`docs/TEST_RESULTS.md`). 스크린샷: `docs/screenshots/20-…~25-…`.

| 확인 | 결과 |

| 홈에서 검색 → 목록 → 정답 후보 상세까지 | 가능. 같은 이름의 파란색 파우치가 두 개 나오고 상태(보관 중/반환 완료)와 발견 장소로 구별됨. "파우치"로 넓히면 오답 후보(남색 파우치)도 나옴 |
| 상세에서 보관 장소 | "발견한 곳 도서관"과 "지금 보관 중인 곳 행정관·학생지원팀"이 따로 보이고, 운영 시간·문의처·수령 절차·"담당자가 소유 여부를 확인" 안내가 있음 |

## 6. 한계

- 모든 점검은 자동화된 브라우저로 했다. 사람이 헤매는 지점, 문구 이해, 걸리는 시간은 확인하지 못했다.
