# SPEC 모호·충돌 사항 정리 (Clarifications & Resolutions)

SPEC §1~§30에서 발견한 명확하지 않은 요구사항, 기술적 제약, 충돌하는 조건들을 정리하고 구현 방향 제안.

---

## 1. 기술적 모호함

### 1-1. 지도 기능의 필수성 vs 선택성

**문제**: 
- §9 "Kakao Maps JavaScript SDK를 이용하여 캠퍼스 지도 기반 조회 기능을 구현한다"
- §23 "카카오맵 JavaScript 키가 제공되지 않은 경우 전체 애플리케이션이 실행되지 않는 문제가 발생하지 않도록 한다"
- **충돌**: 지도는 필수 기능인가, 아니면 선택 사항인가?

**CLAUDE.md 원칙**: "조회 경로 주·지도 보조" (§1). 지도 없어도 목록→상세만으로 모든 과업 완료 가능.

**채택 결정**:
- **지도는 선택적 보조 기능**. Kakao SDK 로드 실패 시:
  1. 조회 화면: 목록·필터·검색만 사용 가능
  2. 신고 화면: 건물 선택 + 상세 입력 (좌표 직접 입력) 사용 가능
  3. 상세 화면: 텍스트로만 위치 표시 (지도 불가)
  4. "시연용 위치 선택" 텍스트로 실제 지도와 명확히 구분

**구현**:
```javascript
// LocationPicker.jsx
const [mapLoaded, setMapLoaded] = useState(false);

useEffect(() => {
  if (window.kakao?.maps) {
    setMapLoaded(true);
  } else {
    setMapLoaded(false); // Fallback UI 렌더링
  }
}, []);

return mapLoaded ? <KakaoMapPicker /> : <BuildingSelector />;
```

### 1-2. 습득물 신고 중 사진 업로드: 실제 vs 예시

**문제**:
- §10 "최대 3장의 사진 업로드...드래그 앤 드롭 업로드...모바일 카메라 및 갤러리 연동"
- §4(연구계획) "사진은 미리 준비한 예시 이미지로 선택 동작만 시험한다"
- **충돌**: 평가 과업 B에서 실제 파일 업로드를 하는가, 아니면 예시 선택만 하는가?

**채택 결정**:
- **평가 과업 B(신고)**: 예시 사진만 사용. "파일 선택" 모달 → 사전 준비된 이미지 목록 선택
- **향후 완전 구현**: 실제 파일 업로드 추가 (범위 조정 대상)
- **UI**: 평가용과 실제용을 구분하지 않음. 기술적으로 동일하되 평가 환경에서는 모의 파일만 제공

```javascript
// PhotoUploader.jsx (평가 환경)
const mockPhotos = [
  { id: 1, url: '/demo-photos/umbrella-1.jpg', label: '검은색 우산' },
  { id: 2, url: '/demo-photos/umbrella-2.jpg', label: '검은색 우산-정면' },
];

// 실제 환경에서는 파일 input 사용
```

### 1-3. 반환 신청 중복 방지: 낙관적 락 vs 비관적 락

**문제**:
- §15 "동일한 물품이 여러 사용자에게 중복 반환되지 않도록 서버에서 트랜잭션 및 동시성 처리를 적용한다"
- §18 "FOUND_ITEMS.version: 반환 동시성 제어용 낙관적 락"
- **기술적 선택**: 낙관적 락(Optimistic Locking, @Version) vs 비관적 락(Pessimistic Locking, FOR UPDATE)?

**CLAUDE.md**: 명확한 선택 없음.

**채택 결정**:
- **낙관적 락 선택** (@Version 필드 사용)
  - 이유: 반환 신청·승인·완료가 순차적 프로세스이고, 충돌 가능성 낮음
  - 성능: 비관적 락보다 동시성 높음
  - 구현: Entity에 @Version 필드 추가, 업데이트 시 버전 체크

```java
@Entity
public class FoundItem {
  @Version
  private Long version;
  // 반환 완료 시 version 업데이트되어 중복 반환 방지
}
```

**대안**: 반환 완료 시 status를 RETURNED로 변경하고, 조회 시 WHERE status != 'RETURNED' 필터 추가 (더 간단할 수 있음)

### 1-4. 소프트 삭제 vs 완전 삭제

**문제**:
- §18 "신고 삭제는 Soft Delete 방식으로 처리한다"
- §18 "삭제된 데이터는 일반 검색, 지도 조회, 추천 결과에서 제외한다"
- **구현 범위**: 모든 쿼리에 WHERE deleted_at IS NULL 필터를 붙여야 하는가?

**채택 결정**:
- **모든 조회 쿼리에 필터 필수**. 단, Repository 베이스 클래스에서 처리:

```java
// BaseRepository (BaseEntity를 extends하는 모든 Repository에 적용)
@Query("SELECT e FROM #{#entityName} e WHERE e.deletedAt IS NULL")
List<E> findAll();

// 개별 쿼리도 항상 명시
"SELECT * FROM found_items WHERE deleted_at IS NULL AND status = ?"
```

## 2. 기능 범위 모호함

### 2-1. 유사 물품 추천 알고리즘

**문제**:
- §17 "초기 유사도 평가 기준: 카테고리 일치(30점), 물품명·특징 유사도(30점), 위치 근접도(25점), 날짜 유사도(15점)"
- §17 "외부 AI API를 사용하지 않고 규칙 기반 점수 계산 방식으로 구현한다"
- **구현 오류**: 물품명·특징 "유사도" 계산 방법이 명확하지 않음 (문자 거리? 토크나이제이션?)

**채택 결정**:
- **범위 외로 분류** (평가 과업 A, B에 미포함, 제안서 §4 제외)
- 필요 시 다음 단계에서 구현:
  - Levenshtein 거리 (문자열 유사도)
  - 토크나이제이션 (단어 기반 비교)
  - Haversine 공식 (위도·경도 거리 계산, 이미 명시됨)

### 2-2. 습득자 보관 중 개인정보 처리

**문제**:
- CLAUDE.md "TEMPORARY(습득자 임시 보관) 물품은 습득자 연락처를 노출하지 않는다"
- 그런데 사용자가 반환을 요청하려면?
- §15 "소유자만 알 수 있는 특징은 일반 사용자에게 공개하지 않는다"
- **충돌**: 공개하지 않으면서 소유 확인을 어떻게 하는가?

**채택 결정**:
- **TEMPORARY 상태일 때 화면 흐름**:
  1. 상세 보기: "습득자가 보관 중 · 반환 신청 시 관리 부서가 연결" 텍스트만 표시
  2. 반환 신청: 사용자가 소유 특징 입력 → 관리 부서가 습득자에게 확인 → 승인/반려
  3. 담당 부서 연락처 표시: 필수
  4. 습득자 연락처: 비노출

```javascript
// FoundItemDetailPage.jsx (TEMPORARY 상태)
{item.custodyType === 'TEMPORARY' ? (
  <p>습득자가 보관 중입니다. 반환 신청 시 관리 부서가 연결해 드립니다.</p>
) : (
  <p>담당부서: {item.storageLocation}</p>
)}
```

### 2-3. 발견 위치 없는 경우 처리

**문제**:
- §8 "발견 장소" 필수 필드
- 그런데 습득자가 "정확한 발견 장소를 모르는" 경우는?
- §10 "분실 위치가 정확하지 않은 경우 여러 장소를 강제로 입력하게 하지 않고 대표 추정 위치와 추가 설명을 입력할 수 있도록 한다" (분실 신고)

**채택 결정**:
- 습득물 신고는 발견 위치 필수 (인수 과정에서 중요)
- 분실 신고는 추정 위치 필수 + 추가 설명 선택 (불확실성 허용)
- UI에서: "발견한 주요 건물/위치"라고 명시

```javascript
// ReportFoundItemPage.jsx
<label>발견한 위치 (필수) *</label>
<input placeholder="예: 도서관 1층" required />
```

## 3. UI/UX 모호함

### 3-1. 모바일 입력 글자 16px - 모든 입력에 적용?

**문제**:
- §5 "모바일 입력 글자는 16px 이상(iOS 확대 방지)"
- 이를 모든 input, textarea, select에 적용하면 모바일에서 과하게 커 보일 수 있음

**채택 결정**:
- **모바일 input만 16px 이상**. 라벨·보조 텍스트는 14px 가능
- CSS 미디어 쿼리로 처리:

```css
@media (max-width: 768px) {
  input, textarea, select {
    font-size: 16px; /* iOS 확대 방지 */
  }
}
```

### 3-2. 발견·보관 위치 아이콘 중복 (§9 vs §12 vs CLAUDE.md)

**문제**:
- §9 "빨간색 마커: 습득물 발견 위치, 파란색 마커: 물품 보관 위치"
- CLAUDE.md "위치를 표시할 때는 항상 '발견 위치(빨강, MapPin)'와 '보관 위치(파랑, Archive)' 등 다른 아이콘 함께 표기"
- **선택**: 색상만 다를 것인가, 아이콘도 다를 것인가?

**채택 결정**:
- **색상 + 아이콘 + 텍스트 라벨 모두 사용**
  - 발견: 빨강 + MapPin 아이콘 + "발견한 곳" 라벨
  - 보관: 파랑 + Archive(또는 다른 아이콘) + "보관 중인 곳" 라벨
  - 이유: 색약자 고려, 명확성 최대화

```javascript
// LocationDisplay.jsx
{foundLocation && (
  <div className="text-red-500">
    <MapPin size={20} /> 발견한 곳: {foundLocation}
  </div>
)}
{storageLocation && (
  <div className="text-blue-500">
    <Archive size={20} /> 보관 중인 곳: {storageLocation}
  </div>
)}
```

### 3-3. 상태 표시: 색상만? 색상 + 텍스트?

## 4. 데이터 규칙 모호함

### 4-1. 시드 데이터의 현실성 수준

**문제**:
- §25 "테스트 데이터에는 실제 개인정보를 포함하지 않는다"
- 그런데 "현실성 있게"는 얼마나?
- 예: 캠퍼스 좌표가 "정확하지 않을 수 있음"인가?

**CLAUDE.md**: "캠퍼스 좌표·건물 정보는 실제 정보처럼 확정하지 않는다. 설정값/DB로 관리하고 시드 데이터는 '시연용'으로 명시"

**채택 결정**:
- 모든 시드 데이터에 "시연용 데이터입니다"라는 명시 필요 (UI에 표시 아님, 코드 주석)
- 좌표: 실제 캠퍼스와 무관한 임의 값 (가상 범위 내)
- 건물명: 실제 대학교 건물명을 참고하되 모두 "시연용"으로 명시
- 물품: 개인 식별 정보 없는 범용 물품만

```sql
-- 시연용 테스트 데이터
-- 모든 좌표는 가상이며 실제 캠퍼스와 무관합니다.
INSERT INTO campus_buildings VALUES
  (1, '도서관(시연용)', 37.123, 127.456, '시연용 위치'),
  (2, '학생회관(시연용)', 37.234, 127.567, '시연용 위치');
```

## 5. 테스트 & 배포 모호함

### 5-1. 테스트 환경: MySQL vs H2

**문제**:
- §3 "데이터베이스: MySQL 8"
- CLAUDE.md "테스트는 H2(MySQL 모드) 프로필 사용"
- 하지만 H2 MySQL 모드가 모든 MySQL 기능을 지원하지 않음

**채택 결정**:
- **개발 환경**: H2 (application-test.yml)
- **최종 테스트**: MySQL 필수 (application.yml)
- **CI/CD (있다면)**: H2로 빠른 테스트, 최종 MySQL 검증
- application.yml 분리:
  ```yaml
  # application.yml (MySQL)
  spring.datasource.url=jdbc:mysql://localhost:3306/thatsmine
  
  # application-test.yml (H2)
  spring.datasource.url=jdbc:h2:mem:testdb;MODE=MySQL
  ```

## 6. 보안 모호함

### 6-1. 사진 파일 경로 조작 방지

**문제**:
- §23 "파일 이름과 저장 경로를 안전하게 처리한다"
- 구체적인 방법이 명시되지 않음

**채택 결정**:
- 저장 파일명: UUID 생성 + 확장자만 보관
- 경로: 사용자 입력 받지 않음, 고정 디렉터리만 사용
- 접근: 파일 ID로만 조회, 경로 직접 접근 불가

```java
// FileUploadUtil.java
String savedFileName = UUID.randomUUID() + "." + originalExtension;
// 저장: /uploads/found-items/{savedFileName}
// DB에는 ID와 메타데이터만 저장
```

### 6-2. JWT 만료 처리

**문제**:
- §13 "JWT 기반 인증"
- JWT 만료 후 갱신(refresh token) 여부?

**채택 결정**:
- **access token 만료 시 재로그인 요구** (refresh token 미구현)
- 이유: 단순성, 평가 과업에 미포함
- 프론트엔드: 401 응답 → 로그인 페이지로 이동

## 최종 정리

| 모호·충돌 항목 | 결정 | 구현 복잡도 |
|-------------|------|----------|
| 지도 필수성 | 선택적 + fallback UI | 중간 |
| 사진 업로드 | 평가: 예시 선택, 향후: 실제 업로드 | 낮음 |
| 반환 중복 방지 | 낙관적 락 | 낮음 |
| 소프트 삭제 필터 | 모든 쿼리에 필수 | 중간 |
| 추천 알고리즘 | 범위 외 | 높음 |
| TEMPORARY 개인정보 | 담당부서만 표시 | 낮음 |
| 발견 위치 필수성 | 습득: 필수, 분실: 필수 | 낮음 |
| 위치 아이콘 | 색상 + 아이콘 + 텍스트 | 낮음 |
| 시드 데이터 현실성 | 모두 "시연용" 명시 | 낮음 |
| 테스트 환경 | H2 개발 → MySQL 최종 | 중간 |
